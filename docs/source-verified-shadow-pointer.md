# Source-verified negative discovery: `golf_field +0x04`

Source: [RPGolFieldManager.h](https://github.com/kiwi515/ogws_info/blob/main/RP/RPSports/RPGolScene/RPGolFieldManager.h) identifies the 0x04 field as `RPGrpShadowTexture *mPlayerShadowTexture` (player shadow), **not the ball**. Thus the previous pointer `0x92583488` and floats at `+0x50` / `0x925834D8` were read from an object reached via the player shadow owner. Coupled with the 240-sample no-shot camera-only test showing 96 movements, it is definitively inappropriate to label as ball world coordinates. The object’s internal +0x50 field has **not** been typed: this does not prove the float values specifically represent a camera transform.

Documented alternatives: `mCurrentPinObj +0x44`, `mCurrentStartObj +0x50`, `mMapPlayerEff +0x94`, `mMapShotLineEff +0x98`, `mMapBallEff +0x9C` (last is a **minimap ball effect**, not ball physics). [RPGolMapObjBase.h](https://github.com/kiwi515/ogws_info/blob/main/RP/RPSports/RPGolScene/RPGolMapObjBase.h) documents a map-object **translation +0x30**, useful for camera-stable landmark controls, NOT automatically live-ball data. The ball physics owner remains unknown.

**Recommended next action:** run an explicitly source-gated, read-only landmark differential for current pin/start map-object translations across tee-idle/aim-only/swing. Use those as world-frame stability controls while examining `mMapBallEff` as a distinct effect, not as verified ball physics. Coordinate with integrator before changing live startup. Avoid deeper speculative dereferences or treating target coordinates as actual ball positions.
